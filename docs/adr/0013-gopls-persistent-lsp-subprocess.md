# gopls is driven as a persistent LSP subprocess, not the gopls CLI

Where Forge supplies the language server itself — the Codex path, via the `forge internal-mcp` subcommand — it drives gopls as a long-lived subprocess speaking LSP over stdio (`jsonrpc2` framing to a `go.lsp.dev/protocol` client), rather than shelling out to the `gopls` command line per query. The persistent session performs the LSP `initialize` handshake once and reuses the connection for every capability call in that invocation, opening documents lazily (`didOpen`) as they are referenced.

This is forced by two earlier decisions. Capability gating registers an agent-facing tool only when the server's `initialize` response advertises the matching operation — the tool surface is the intersection of requested capabilities with the server's reported capabilities — and only an LSP session produces that response; the CLI does not. And the `gopls` CLI is explicitly non-stable and lacks a `typeHierarchy` subcommand, so it cannot cover the required capability set. The trade-off is a more involved client — handshake, document sync with 0-based↔1-based position conversion at the boundary, readiness-with-timeout, restart-once crash recovery — against the CLI's simplicity; the fidelity and the capability-reporting the gating model depends on make the persistent session the only workable choice.

`go.lsp.dev/protocol` is pinned at v1.0.1 (a revived v1.x line implementing LSP 3.18.0); `sourcegraph/go-lsp` is a types-only fallback. In v1 this driver runs inside the Codex-spawned `forge internal-mcp` process; on the Claude path gopls is launched by Claude's own native LSP client from a Forge-supplied plugin, so the driver is not used there. A future Forge-owned MCP endpoint that reuses one gopls across an Issue's repair loop (rather than re-indexing per invocation) is noted but not built.
