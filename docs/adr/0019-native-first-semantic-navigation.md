# Semantic navigation is native-first: use the harness's own LSP, fill only the gaps

Forge gives agents language-aware code navigation (definitions, references, implementations, hover, symbols, call/type hierarchy) capability-first: when the agent's harness already exposes a semantic operation natively, Forge uses it and does not run a competing language server for that capability. A backend declares a Semantic Profile — the native Semantic Capabilities it exposes plus the Injection Channel through which Forge can supply what it lacks — and a `SemanticProvider` selects native-vs-fill per capability. Claude Code (native `LSP` tool, nine operations) keeps its own tooling; Forge supplies gopls behind it, via Claude's own `.lsp.json` plugin mechanism, only where a server is missing. Codex, which has no native LSP, is served entirely by a Forge-managed language server exposed over MCP. No worktree ever runs two language servers for one language.

The rejected alternative was a uniform Forge-owned MCP+gopls channel used for every backend, suppressing Claude's native `LSP`. It is simpler — one code path, one tool surface — but it duplicates a capability the harness already provides (contrary to the requirement in issue #79), discards Claude's already-tuned LSP tool, and pays to run a redundant server. Native-first costs a second fulfillment path — the price the `internal/semantic.Provider` seam is built to absorb — but it honors the no-redundant-server principle and lets each harness contribute what it does best.

Selection is by *declared capability, never by harness identity*, so the model stays backend-neutral even though only Claude Code is wired for end-to-end validation today. The provider is best-effort: any provisioning failure degrades to no semantic navigation rather than failing the Worker, and per-capability degradation never cascades. v1 is Go-first (gopls) and wires the execution path only; the planning agent is a designed-in but not-yet-wired future caller.
