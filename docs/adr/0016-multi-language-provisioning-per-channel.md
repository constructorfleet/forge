# Multi-language semantic navigation is provisioned per channel: a multiplexing MCP server on the forge-managed path, an adapter-local plugin on the native path

Extending semantic navigation from Go to TypeScript, Python, and Rust is done differently on each delivery channel, because the two channels have different shapes. On the **forge-managed path** (the Codex backend, which has no native LSP), the single `forge internal-mcp --workspace` subcommand becomes a *multiplexer*: it detects the workspace's languages, maps them through the Language Server Registry, starts one `lspdriver` per detected server, and routes each tool call to the driver whose language matches the file argument's extension — `search_symbols{scope:workspace}` fans out across all drivers and merges. One MCP server exposes one set of un-namespaced tools (`find_definition`, …), and the Codex adapter registers exactly one `forgelsp`. On the **native path** (Claude Code, which drives its own LSP), the adapter writes one session-only `.lsp.json` holding an entry per detected server, translating each server's language to the file extensions and Anthropic language identifiers Claude's native LSP tool expects — a mapping kept as a table in the Claude adapter, since `.tsx → typescriptreact` and friends are Claude's `.lsp.json` vocabulary, not the registry's.

The one-multiplexer choice is forced by tool-name uniqueness and the "never two servers per worktree" invariant. Running one MCP server per language would give the agent several identically named `find_definition` tools to disambiguate; routing by extension inside a single server avoids that. For the same invariant, the Node/JavaScript/TypeScript family maps to a single registry key served by typescript-language-server (which serves both `.js` and `.ts`), so a repository is never detected as two languages that would start two servers. TypeScript's server is given no injected `tsserver.path`: matching Anthropic's own official plugin, Forge relies on the workspace's own `node_modules/typescript`, and if it is absent the server simply fails to `initialize` and that language degrades to inert — never a failed Worker.

The declared per-backend Semantic Profile stays coarse and is not split by language. It models what the *harness's own tooling* exposes (Claude's fixed native-LSP operation set; Codex's none), which does not vary by language; the *language server's* capabilities — pyright lacking `implementation`, only gopls advertising `typeHierarchy` — are a separate question answered at runtime by each driver's `initialize` response, which gates the forge-managed tool surface per driver. A per-language declared profile would change no selection outcome: on the native path Forge cannot fill a per-language gap without a second server anyway, and on the forge-managed path runtime gating already covers it. The remaining case — supplementing an operation the native harness exposes but the underlying server cannot answer — is left to a future harness-native passthrough, the first place per-(backend × language) capability knowledge would actually be needed.

This honors [ADR 0012](0012-native-first-semantic-navigation.md) (native-first: never duplicate a server the harness already drives) across all four languages, and builds on [ADR 0015](0015-language-neutral-lsp-driver.md) (one driver, per-server profiles). The trade-off inherited from the Go path stands: the Codex-spawned `internal-mcp` re-indexes per invocation; a Forge-owned endpoint reusing servers across an Issue's repair loop is noted but not built.
