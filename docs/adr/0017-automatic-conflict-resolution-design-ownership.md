# Automatic conflict resolution has no design yet; this ADR is a placeholder that owns scoping it

No prior design for automatic merge-conflict resolution exists anywhere in this repository — not in `docs/adr/` (ADRs 0001-0016 cover storage, dependency semantics, execution scheduling, and semantic navigation, none of them conflicts) and not in `.scratch/` (no wayfinding map or spec mentions conflict resolution). `internal/ci/conflict.go`'s `pollConflict` doc comment states the current behavior plainly: "Forge attempts no automatic conflict resolution... every conflict stops the run for a human rather than guessing at a resolution." Issue [#232](https://github.com/constructorfleet/forge/issues/232) proposes building that capability but was itself scoped as a follow-up rather than a design, and issue [#231](https://github.com/constructorfleet/forge/issues/231) (the CI-status-check bug whose repro first surfaced the gap) explicitly deferred conflict resolution as out of scope. This ADR is the design's owner going forward: no implementation should attempt automatic conflict resolution until it either records a decision here or supersedes this ADR with one that does.

Three questions must be answered before any implementation work starts:

- **Which conflict shapes are safe to auto-resolve.** A textual three-way merge with no overlapping hunks (e.g. the PR's branch and its base touched disjoint regions of a file) is a plausible candidate; anything involving overlapping hunks, renames, deletes-vs-edits, or binary files is not, and must keep routing to `NEEDS_INFO` as it does today. The boundary needs to be defined precisely enough that `pollConflict` (or its replacement) can classify a conflict deterministically rather than guessing.
- **Rollback semantics if gates fail post-resolution.** An auto-resolved merge must still pass the same quality gates (build, lint, test) a normal execution does before it can be considered successful. If gates fail after a resolution attempt, the workspace must be restored to its pre-resolution state and the run must fall back to `NEEDS_INFO` exactly as an unresolvable conflict does today — an auto-resolution attempt must never leave a run in a worse or more ambiguous state than doing nothing would have.
- **Workspace/branch restoration behavior.** Attempting a resolution necessarily mutates the workspace (merge commit, working tree changes) and potentially the remote branch (if pushed). The design must specify how that mutation is contained and undone on failure — e.g. attempting the merge in a disposable location before touching the tracked branch, or reverting/force-pushing on failure — consistent with this repo's existing retry/resume semantics ([ADR 0007](0007-separate-retry-budgets.md), [ADR 0011](0011-retry-refreshes-base-in-flight-resume-does-not.md)).

This ADR intentionally does not answer these questions; it exists to be the citable, discoverable anchor that issues #231 and #232 point to, so that "no automatic conflict resolution design exists" stops being an implicit fact buried in a doc comment and becomes an explicit, linkable one.
