# The Forge-managed tool surface is seven capability-gated tools normalizing to one Source Location schema

Where Forge fulfils Semantic Navigation itself — the Codex path today, any future non-native backend tomorrow — it exposes a consolidated, agent-facing tool surface of up to seven tools, one per Semantic Capability: `find_definition`, `find_references`, `find_implementations`, `symbol_info` (merging hover, type, signature, and docs into one call), `search_symbols` (parameterized by `scope: file|workspace`, merging document and workspace symbol search), `call_hierarchy`, and `type_hierarchy`. This is deliberately coarser than the underlying LSP request set (which splits hover/signatureHelp/typeDefinition and document/workspace symbols) because the agent-facing surface optimizes for fewest decisions per navigation intent, not for a 1:1 protocol mirror. Claude Code's native `LSP` tool is untouched by this decision — it keeps its own nine-operation shape — so the two surfaces are intentionally non-uniform across backends; this ADR governs only the Forge-managed side.

Every tool resolves to one normalized result schema, extending the glossary's Source Location: `{file, line, column?, end_line?, end_column?, snippet?}`, returned as a single Source Location for singular capabilities (`find_definition`, `symbol_info`'s location) or a list for plural ones (`find_references`, `find_implementations`, `search_symbols`, the flattened nodes of `call_hierarchy`/`type_hierarchy`). `symbol_info` additionally carries `{name, kind, type_signature?, documentation?}` alongside its Source Location — hover/signature content that isn't itself a location but is always emitted next to one, preserving "every tool normalizes to a Source Location a subsequent Read can act on" as the load-bearing contract. This schema is Forge-internal only: it is not imposed on or shared with Claude's native `LSP` output, since ADR-0012 already committed to per-backend tool shapes and unifying the wire schema now would require translating Claude's native results through a shape it didn't produce, for no consuming code that needs it.

`call_hierarchy` and `type_hierarchy` are gated behind capability: a Semantic Provider that finds the underlying server did not advertise the capability in its `initialize` response (per ADR-0013's gating principle) omits the tool from the agent's tool list entirely, rather than registering it and returning an "unsupported" error. The other five tools are treated as baseline-required for any backend receiving a Semantic Profile — a server missing one of those is a degraded provider, handled by ADR-0012's existing best-effort/degrade-safe fallback (no Semantic Navigation), not by a partial tool list. Omission-over-error was chosen because an agent that never sees a tool never wastes a turn attempting it or handling its failure; the alternative (register everything, fail at call time) was rejected as pure overhead with no compensating benefit, since capability is known statically at provider setup, before any tool list is handed to the agent.

Reference and symbol lists are capped at 50 results per call, sorted by the server's native ranking (definition proximity for references, alphabetical-then-path for symbol search) with no cursor-based pagination in v1: a truncated result carries a `truncated: true` flag and a `total_count`, and an agent that needs more either narrows `search_symbols`'s query or scope, or is expected to accept the top slice. This was chosen over pagination because the agents primarily consuming these tools (execution Workers navigating toward a specific edit) act on the first few highest-relevance results in practice; a stateful pagination cursor would add protocol surface and provider-side state for a case the truncation flag already makes legible. If the planning agent (a designed-in but not-yet-wired future caller, per ADR-0012) turns out to need exhaustive enumeration, that reopens this cap rather than being solved speculatively now.
