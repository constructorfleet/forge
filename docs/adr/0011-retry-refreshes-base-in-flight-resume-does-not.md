# Retry refreshes a Worker's base forward; in-flight resume does not

`forge retry` re-resolves a FAILED Issue's Worker base to the target branch's current tip before re-running it, rebasing the existing Workspace onto that tip (or branching fresh from it, if none exists). This is a forward-only move: the refresh is refused unless the new tip still descends from the previously captured base, so every already-merged Dependency that base captured (ADR 0005/0006) remains present — a refresh can only add already-merged commits, never drop one. A rebase conflict is reported as a distinct outcome naming the conflicting paths, and leaves the Issue FAILED rather than silently applying a partial move.

`ResumeExecution`'s in-flight resume paths (recovering a still-running Worker after an orchestrator restart) do not refresh the base — they keep exactly the base ADR 0006 captured at the Issue's original READY transition. A Worker mid-flight is not "a fresh attempt" the way a retried, terminal FAILED Issue already implies; moving its base out from under it would risk invalidating in-progress work with no analogous "fresh retry" justification. The base refresh is scoped to `RetryIssue` alone.
