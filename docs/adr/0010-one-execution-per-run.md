# One Execution per `forge execute` run

A single `forge execute a b c` invocation is one Execution spanning all of its Issues, per CONTEXT.md's definition of Execution as "a user-requested orchestration run over one or more Issues." Ticket 26's Scheduler currently dispatches each requested Issue through `engine.Engine.Execute` unchanged, and `Engine.Execute` mints and persists its own fresh Execution row per call — so today, `forge execute a b c` produces three separate Executions, one per Issue, not the one shared Execution the domain model calls for. This was a deliberate scope decision to keep ticket 26 additive against `Engine.Execute`'s body while ticket 20 (Review stage) and ticket 21 (retry loop) were touching it concurrently, not an endorsement of one-Execution-per-Issue as correct. Realizing one shared Execution requires `Engine.Execute` (or a new Engine entry point) to accept a caller-supplied Execution rather than always creating its own — a real signature change, tracked as follow-up ticket 26b, which must land before ticket 30 (concurrent execution isolation) and ticket 32 (operational CLI) since both assume one Execution addresses a whole multi-issue run. Until 26b lands, `forge status <execution-id>` only ever shows one Issue's slice of a multi-issue `forge execute` call — a known interim limitation, not the target design.
