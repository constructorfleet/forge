# The Forge-managed LSP driver is language-neutral, with per-server behavior carried as declarative data

The Forge-managed language-server driver (`internal/semantic/gopls`, renamed to `internal/semantic/lspdriver`) is one deep module that speaks LSP to *any* server, not a gopls-specific one. Its lifecycle machinery — spawning the subprocess, the `initialize`/`initialized` handshake, readiness-with-timeout, restart-once crash recovery, lazy `didOpen`, and reporting the server's advertised `Capabilities()` — was already language-neutral; only a handful of response-shape assumptions were gopls-specific. Those are lifted out into a declarative **`ServerProfile`** value carried per server: the `initializationOptions` to send, a `HoverStyle` selector for how to split a hover into signature and documentation, and a flag for whether to drop child symbols from `documentSymbol`. The profile is a plain data value (an enum and two fields, not function pointers), its type defined in the driver package and its instances constructed in and embedded by the Language Server Registry (`internal/lsp`), so a language server is added by adding a registry row — never by writing a new driver type.

This is forced by real per-server variance that a single gopls-shaped parser gets wrong. rust-analyzer's hover emits two fenced blocks — the first is the crate/module path, the second the actual signature — so gopls's "first fence is the signature" rule returns the wrong text; pyright prefixes its hover signature with a `(function)`/`(class)` kind annotation and emits function parameters as child symbols; typescript-language-server refuses to `initialize` without a resolvable workspace `typescript` and therefore needs an init-options hook. Keeping one module with an injected declarative profile — rather than a base driver with per-server subtypes overriding methods — preserves the deep-module shape (a small capability-named interface hiding the protocol) and keeps the per-server differences as data the registry and tests can compare directly.

This decision also closes a latent correctness gap the generalization exposed: the driver's `FindImplementations` called `textDocument/implementation` unconditionally, while call- and type-hierarchy were already gated on the server's advertised capabilities. pyright advertises no `implementationProvider`, so the ungated call would error rather than degrade; implementations are now gated the same way, returning `ErrCapabilityUnsupported` so a missing capability degrades gracefully like every other.

It extends [ADR 0013](0013-gopls-persistent-lsp-subprocess.md): the persistent-subprocess decision stands unchanged; what generalizes is the identity of the server behind it. Capability discovery remains driven purely by the `initialize` response, so per-language capability differences (only gopls advertises `typeHierarchy`; pyright lacks `implementation`) are learned at runtime and need no per-language declaration.
